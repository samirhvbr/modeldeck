# Keys with riders — design (issue #500)

_Design lane, 2026-08-17. Deliverable of #500: the grilling-approved keys-with-riders
change (close record ruling 5), designed within decisions 0002 (stock pin), 0006
(never auth files), 0032/0033/0034, and the discard-hardening. No implementation in
this lane. Auth-adjacent: security lens + full review mandatory (never-compromise #3);
the threat model in §3 is the core of this document, not an appendix._

**Settled and not relitigated here:** the change itself is approved with riders
(ruling 5); the product spends no quota (0032); agent-state reads stay off live
harness DBs (0034); proxy auth files are untouchable (0006). This doc designs the
*how*.

---

## 1. What exists today (grounded, file:line)

- **One shared client key, provisioned by nobody.** Every proxy-routed Claude
  profile gets the same `apiKeyHelper` string — `security find-generic-password -s
  cli-proxy-api-client -w` ([service.mjs:144](../src/service.mjs)) — and the same
  Keychain-pointer block in the pinned shell env file
  ([adapters/claude.mjs:298, 349](../src/adapters/claude.mjs)). **No code in the
  repo creates the `cli-proxy-api-client` Keychain item or writes an `api-keys`
  list into the live proxy config.** The seeded managed config carries no
  `api-keys` at all ([ManagedProxyLive.swift:177-191](../macos/ModelDeckMac/Sources/ModelDeckMacCore/ManagedProxyLive.swift));
  only the build handshake and the compat suite write one, with placeholders.
  The helper is deliberately best-effort (`|| true`; a missing item exports
  nothing). **Correction to the issue's framing:** the blocker is not just that
  the helper is *shared* — client-key provisioning as a whole is an unbuilt,
  manual, out-of-band step. This design builds it.
- **The config writer is seed-only.** `ensureConfig` returns immediately when a
  config exists ([ManagedProxyLive.swift:141](../macos/ModelDeckMac/Sources/ModelDeckMacCore/ManagedProxyLive.swift));
  every write passes `ManagedProxyWriteGuard.requirePermittedWrite`, which admits
  exactly two destinations — `config.yaml` and seed-time `.mgmt-key`
  ([ManagedProxy.swift:72-123](../macos/ModelDeckMac/Sources/ModelDeckMacCore/ManagedProxy.swift)).
  Secret-bearing files are published 0600-from-birth via mkstemp +
  `renamex_np(RENAME_EXCL)`.
- **Ingest is an explicit allowlist.** `parseUsageRecord` constructs its return
  object field by field; `api_key`, `access_token_sha256`, `response_headers`
  (which carry the provider `Request-Id` and rate-limit headers), raw UA/IP and
  failure bodies can never reach SQLite
  ([usage-ingest.mjs:63-137](../src/usage-ingest.mjs)). This hardening **stands**;
  the riders are added as new allowlist fields, not by loosening it.
- **`request_usage`** ([db.mjs:675-714](../src/db.mjs)) resolves Claude rows to
  accounts by identity; the routing writer refuses to touch a foreign base URL or
  helper ([service.mjs:4104-4126](../src/service.mjs)) and the helper key is only
  exported for loopback base URLs (`isLoopbackUrl`,
  [service.mjs:150-162](../src/service.mjs)).

## 2. Design

### 2.1 Key model

- **One client key per Claude profile**, generated by ModelDeck: 32 random bytes,
  base64url unpadded — the same shape and generator discipline as the management
  secret ([ManagedProxyLive.swift:197-205](../macos/ModelDeckMac/Sources/ModelDeckMacCore/ManagedProxyLive.swift)).
  These are **ModelDeck-generated local proxy client keys, not provider
  credentials** — 0016's "never touch tokens" and 0006's auth-file rule are about
  provider credential material and are untouched. Nothing here reads, writes, or
  copies an OAuth token.
- **At rest:** one Keychain generic-password item per profile, under a
  **per-profile service name**: `cli-proxy-api-client.<profile-slug>`, where the
  slug is the profile's **stable machine identifier** (account id; charset
  `[a-z0-9-]`), never the free-text label. The legacy shared item keeps the
  service `cli-proxy-api-client` **exclusively** — per-profile items must be
  unreachable by the legacy `-s cli-proxy-api-client` lookup, because
  `find-generic-password` without `-a` returns the *first match*: items sharing
  the legacy service would let a stale shell or a not-yet-reactivated profile
  (the pinned env file is only rewritten at activation) fetch another profile's
  key and silently mis-attribute (security review of #506, blocker 1). The
  service name alone disambiguates; no `-a` flag is needed. The free-text label
  appears only in SQLite/UI. The slug is the only new value interpolated into
  `apiKeyHelper` command strings and shell files — a charset-restricted machine
  id makes injection structurally impossible (§3.5). **Provisioning is
  deterministic** (CodeRabbit, CWE-345): writing a profile's item is
  create-or-replace under its service name — any existing item(s) under that
  service are removed and the single new item written, so duplicates cannot
  accumulate and a re-provision always converges on one item holding the
  current key; on rotation, the old value dies with the replaced item, and the
  config/mapping updates follow (§2.1 report, §2.6 write path). Duplicate
  handling, replacement, and rotation cleanup are named test cases in build
  item 3.
- **In the proxy config:** all profile keys appended to the stock `api-keys`
  list (decision 0002's named no-fork lever). The config already carries the
  management secret in plain text at 0600 (the #431 ruling: a second encrypted
  copy adds complexity, not secrecy); client keys get the identical treatment.
- **Ownership of raw keys:** the **Swift app** generates keys, writes Keychain
  items, and writes the config — it is already the only config writer. The
  **daemon never retains a raw client key** (the queue consumer holds one
  tick-locally before hash-and-drop — §3.1). The app reports `{sha256(key) →
  profile_id, label}` to the daemon over the existing authenticated report
  channel; the daemon persists that mapping and resolves attribution from it.
  The report is **idempotent and full-state**, with defined replacement
  semantics (CodeRabbit, PR #506): the app re-reports the complete mapping on
  every launch/daemon handshake; the daemon applies each report **atomically**
  (one transaction) as a full replacement — entries absent from the report are
  deleted, so a key rotation or profile removal takes effect at the next
  report and a removed key thereafter resolves to honest NULL. Each report
  carries a **monotonic generation** persisted app-side; the daemon records
  the last applied generation and **rejects older reports**, so replay or
  out-of-order delivery can never resurrect a rotated key or a removed
  profile. Replay, rotation, and removal are named test cases in build item 3.
  This self-heals a rebuilt daemon DB or a report lost in flight instead of
  leaving requests permanently unattributed (review nit 10).

### 2.2 Attribution at ingest

- The proxy's usage records carry an `api_key` field (today discarded). The
  queue consumer hashes it **immediately on parse** (SHA-256), resolves the hash
  against the daemon's mapping, and passes only the resolved **profile label**
  (plus stable profile id for the mapping's own bookkeeping — see D4) into the
  allowlist object. The raw key value is tick-local, exactly like the management
  key ([usage-queue-consumer.mjs:91-99](../src/usage-queue-consumer.mjs)): never
  retained on the consumer, never logged, never in a warning string.
- **Unknown key** (not in the mapping): label stays NULL. The unknown key value
  — raw or hashed — is **never** stored or logged; at most a count
  (`unattributed=N`) joins the existing counts-only log contract.
- New column: `request_usage.profile_label TEXT` (nullable; historical rows
  NULL). Label is captured as-at-ingest; a later profile rename does not rewrite
  history (accepted consequence of the label ruling — clarification D4).
  **Labels must be unambiguous among key-enabled profiles** (CodeRabbit, PR
  #506): the accounts table does not require unique labels
  ([db.mjs:660](../src/db.mjs)), and two key-enabled profiles sharing a label
  would produce indistinguishable receipts. Since rows store the label only
  (the ruling), enabling per-profile keys **refuses a duplicate label** with an
  honest rename prompt — collision rejected at provisioning, not disambiguated
  at read time.
- The mapping store: a daemon-owned SQLite table `client_key_map(key_sha256
  TEXT PRIMARY KEY, profile_id TEXT, profile_label TEXT, created_at)` — hashes
  of ModelDeck-generated 256-bit random keys, which are not recoverable key
  material. The discard-hardening invariant ("the per-request `api_key` field
  never reaches SQLite") stands unmodified; the tripwire test extends to assert
  the ingest object still has no `api_key`/raw-key-shaped field (D1).

### 2.3 Rider 1 — response `Request-Id`

- New column: `request_usage.provider_request_id TEXT` (nullable), taken from
  the response `Request-Id` inside the record's response-header data.
- Parse discipline (§3.4): header-name lookup is case-insensitive (HTTP field
  names are; an exact-case `Request-Id` match would silently NULL valid ids);
  value length ≤ 128, charset allowlist `[A-Za-z0-9_.-]`, anything else →
  NULL. The header allowlist extracts **this one header**; the
  `response_headers` blob as a whole remains discarded.
- Purpose: reopens the FINDINGS-336 transcript-join candidate (the join
  returned 0% when we had no request-side id to join on). A build item files a
  spike re-running the join with real ids.

### 2.4 Rider 2 — parsed rate-limit headers

- **Parsed values only, never raw blobs** (ruling 5's wording). New nullable
  columns on `request_usage`:
  - `limit_used_percent REAL` — values outside [0, 100] are rejected to NULL
    (counted, never logged by value) — never clamped: a clamp stores a
    valid-looking number for hostile or garbage input and would bias the
    exhaustion forecast;
  - `limit_status TEXT` — enum allowlist (e.g. `allowed`, `allowed_warning`,
    `rejected`; unknown → NULL);
  - `limit_resets_at TEXT` — ISO-8601, parsed from the provider's epoch/date
    form, rejected unless it lands within a sane window (±400 days of
    observed_at).
- One parser per provider over a named-header allowlist (Anthropic's unified
  rate-limit headers; Codex's used-percent/reset headers), living next to
  `parseUsageRecord` with the same defensive posture: header names matched
  case-insensitively, out-of-range numbers rejected to NULL (never clamped),
  enums allowlisted, everything else NULL, no value ever logged. The exact
  header names present in the pinned proxy's records are verification item V4.
- Value: per-request headroom — the measured "how close to the wall was I at
  this moment" that turns the exhaustion forecast (Receipts v1) from
  snapshot-interpolated to per-request ground truth, consistent with 0019
  (provider-denominated percent is the ground truth).
- Retention: all rider columns inherit the ~13-month `request_usage` bound
  (ruling 6) — no separate store, nothing outlives the row.

### 2.5 Per-profile Keychain helper

- `apiKeyHelper` becomes per-profile:
  `security find-generic-password -s cli-proxy-api-client.<profile-slug> -w` —
  the per-profile **service name** disambiguates alone (§2.1, blocker 1: a
  shared service with `-a` accounts would leave the legacy `-s`-only lookup
  matching whichever item comes first). Same change in the pinned shell env
  block and the one-line preview snippet
  ([adapters/claude.mjs:292-374](../src/adapters/claude.mjs)) — same xtrace
  suspension, same pointer-only/no-secret-on-disk property, same
  missing-item-exports-nothing behavior.
- The foreign-helper guard ([service.mjs:4114](../src/service.mjs)) currently
  string-compares against the one shared helper. Recognition as "ours" requires
  **proven ownership, not pattern inference** (review should-fix 7 as
  sharpened by CodeRabbit): ModelDeck records, per profile, the exact helper
  string it last wrote (alongside the provisioning record it already keeps for
  config entries), and a helper is "ours" only when it exactly matches that
  profile's recorded written state (legacy shared form included, recorded at
  migration). A string that merely *looks* generated — right pattern, even a
  known slug — but has no matching ownership record may be the user's own
  hand-authored configuration (including deliberate cross-profile wiring) and
  gets the existing 409 refusal ([service.mjs:4104-4126](../src/service.mjs)),
  never an overwrite or delete — the #282 class. Wire/unwire mutate only
  record-matched helpers; anything else is surfaced, stated, and left alone.
- **Migration from the shared item:** existing installs using the shared
  `cli-proxy-api-client` item keep working — the legacy helper remains valid
  ("ours") until the user enables per-profile keys; enabling migrates each
  routed profile's settings to its own item, and the shared item is left in
  place untouched (it is user-created; removing it is offered, never automatic).
  **Live-session continuity (blocker 2):** shells that fetched the legacy key
  at startup keep sending it for their whole lifetime (the env is read once,
  #278) — so the migration **appends the shared item's current value, when one
  exists, to the `api-keys` list** alongside the per-profile keys. Those
  requests resolve to label NULL per §2.2 — honest "unattributed", never
  guessed — and nothing 401s mid-run. **Domain collision** (CodeRabbit, PR
  #506): attribution is keyed by `sha256(key)`, so if the legacy shared value
  equals a managed profile key (realistically: the user copied a managed key
  into the shared item — random collision is negligible at 256 bits), the
  legacy hash would resolve to that profile and misattribute legacy traffic.
  Migration therefore compares the legacy value's hash against the managed
  set: on a match, the affected profile's key is **rotated at migration**
  (ModelDeck generates these; rotation is cheap) so the legacy and per-profile
  hash domains are provably disjoint before any mapping entry ships; until
  disjoint, the colliding hash resolves NULL. The legacy value is handled
  app-side under the same raw-key discipline as our own keys (§2.1) and is
  removed from the list only by the user's explicit choice, in the same
  consented write path.

### 2.6 Consented config write path (adopted installs)

Today an existing config is **never** modified — that rule is what makes
adoption non-destructive (0008, #398). Per-profile keys require adding entries
to an existing config's `api-keys` list, so ruling 5 names a **consented** write
path. Design:

- **A separate, explicitly consent-gated operation** — `ensureConfig` stays
  seed-only and untouched. The new operation runs only from a consent screen
  that shows, before anything happens: the exact file
  (`~/.config/cliproxyapi/config.yaml`), the exact changes (append N named
  entries to `api-keys` and, when the file is looser than 0600, tighten its
  mode — nothing else), where the timestamped backup will be
  kept, and how to undo (per 0008's visible-handover / 0011's
  one-prompt-never-silent posture). Declining leaves everything as-is with
  per-profile attribution shown as unavailable, with the stated reason —
  honest-coexist, not nagging.
- **Backup first:** a timestamped copy written 0600-from-birth into
  **ModelDeck's own Application Support state dir**, not the proxy dir — the
  write guard keeps admitting exactly two proxy-dir destinations (D2). The
  backup contains client keys and the management secret, so it gets the full
  secret-file discipline and is pruned with a small retained count.
- **Surgical textual append, not a YAML round-trip:** a YAML re-serialize would
  destroy user comments/formatting — a soft form of the destruction the
  never-modify rule exists to prevent. Instead: parse to locate the `api-keys`
  sequence, append our entries textually (or add the block if absent), then
  **verify**: re-parse and assert the parsed document differs from the original
  in exactly the `api-keys` additions and nothing else. Any config the editor
  cannot confidently edit (anchors, includes, unexpected structure, parse
  failure) → **refuse before writing**, with an honest error naming the file
  and a copy-pasteable manual snippet. Write is mkstemp + atomic rename.
  **TOCTOU guard (review should-fix 3):** the proxy's own management API can
  rewrite the config between our read and our rename — immediately before the
  rename, the target is re-read and byte-compared against the originally-read
  bytes; a mismatch aborts the publish, and the operation re-runs
  parse-append from the fresh bytes (bounded retries) or refuses loudly.
  **Every retry re-baselines its rollback state** (CodeRabbit, PR #506): each
  attempt captures its own pre-write bytes and writes its own backup before
  publishing, and any later rollback restores only the *current* attempt's
  snapshot — reusing the first attempt's snapshot after a retry would restore
  stale bytes over the very intervening change the retry detected. The same
  pre-restore byte-compare guards the rollback path.
  **Residual window (CodeRabbit, PR #506 — accepted risk, recorded):** the
  compare-to-rename gap cannot be closed unilaterally. The concurrent writer
  is a separate Go process that honors no advisory lock, and macOS rename over
  an existing path cannot be made conditional on content — exclusive
  coordination would require proxy-side cooperation the stock pin does not
  offer (0002), and refusing the operation outright wherever a proxy runs
  would disable the consented path everywhere it exists to serve. The design
  instead (a) narrows the window to the microseconds between compare and
  rename, (b) performs the edit only at consented, user-initiated moments
  with ModelDeck's own management-API mutations paused, and (c) re-reads and
  verifies after publish, so a lost concurrent write is detected and reported
  loudly rather than silently absorbed. Blast radius if the window is ever
  hit: one management-API config change, recoverable only if the proxy
  re-persists it — stated here so the sign-off covers it.
  **Permissions (review should-fix 4):** an adopted config may sit at 0644 —
  appending fresh key material to a world-readable file is a leak, and
  "preserve mode" is wrong here. The consented change **includes tightening
  the file to 0600**, named explicitly on the consent screen; if the tighten
  cannot be performed, the operation refuses with a copy-pasteable `chmod 600`
  snippet instead of writing.
- **Failure/rollback:** post-write verify failure → restore the pre-write bytes
  (kept in memory and as the backup) via the same atomic path — guarded by the
  same pre-restore byte-compare (should-fix 3) — and report loudly. Disabling
  the feature (or "Stop Managing") removes exactly the entries recorded in
  the provisioning record — and value-match alone cannot prove an entry is
  ours: if a provisioned key's value appears in `api-keys` more times than we
  added it (a user copied a managed key into their own entry), the automatic
  removal refuses and surfaces the duplicate for the user to resolve, rather
  than deleting an entry the user placed — under the same verify-and-refuse
  discipline.
  **Removal is not complete at file-write (review should-fix 6):** the proxy
  keeps honoring removed keys until its config is actually reloaded, so
  removal shows the same honest "pending restart" state as enablement, and
  the feature reports removal as *live* only once verified (restart observed,
  or hot-reload confirmed per V3). Secret-bearing backups must not silently
  outlive the keys they contain: once removal is verified live, the UI offers
  deletion of the now-stale backups; until then they are retained as the
  rollback path.
- **Activation choreography:** `api-keys` is read from `config.yaml`, and
  restarting the proxy kills live streams (the standing rebalancer rule). For a
  **managed** proxy: the config edit is applied immediately, and the restart
  that makes it live happens on the user's explicit "restart now" (the consent
  screen offers it) or the next natural lifecycle restart — never an automatic
  mid-stream bounce. For a **coexist** (foreign) proxy, ModelDeck does not own
  the process — and it may not even run against the default config path: the
  proxy takes `-config <file>`, so **the target file is derived, never
  defaulted** (review should-fix 5) — from the running process's arguments /
  the adoption record, per the 0009/0010 detection-and-identification
  discipline. When the actual config path cannot be established, the write is
  **refused** with an honest explanation — writing the default-path file would
  plant raw keys in a file the proxy never reads and show "pending" forever.
  Once written, the feature shows honest "pending your proxy restart" until
  requests carrying the new keys appear. Whether the pinned proxy hot-reloads
  `config.yaml` is verification item V3; if it does, this simplifies to "takes
  effect automatically."
- **Enforcement-flip gate (blocker 2):** if V2 finds that an empty/absent
  `api-keys` list means accept-all, then writing the first list entry **flips
  the proxy to enforce-list** and would hard-401 every client not carrying a
  listed key — including live sessions whose env was read once at shell start.
  §2.5's legacy-value append covers clients on the shared key; clients sending
  **no** key at all have no such cover. This is a **gate on shipping the write
  path, not a consent-screen sentence**: the build item may not ship until
  V2's answer is in hand and the design of this bullet is confirmed or
  amended against it (e.g. requiring pre-flight evidence that all observed
  clients carry a key before the first write is offered).

### 2.7 Scope boundary — Codex

Codex routing is user-owned config ModelDeck neither writes nor verifies (the
recorded asymmetry). This design is **Claude-first**: per-profile keys wire only
through the Claude settings/shell writers. Codex requests keep resolving as
today; a Codex parity item is filed, gated on Codex routing becoming managed at
all (D5).

## 3. Threat model (the core)

Assets: (A1) per-profile client keys — spend the user's subscription via their
loopback proxy, read model outputs; (A2) the management secret — already in
the config, unchanged here; (A3) provider OAuth tokens — **never touched by
this design**; (A4) attribution integrity — receipts must not lie; (A5) the
user's existing proxy config — must never be corrupted or silently changed.

Honest baseline stated up front: the proxy listens on loopback and every asset
here is same-user-readable by design (Keychain items readable via `security`,
config at 0600). **A malicious same-user process already owns the session** —
it can read the shared key today, the per-profile keys tomorrow, or the OAuth
flow directly. Per-profile keys are an **attribution and mis-wiring-prevention
mechanism, not a local privilege boundary**, and nothing in the product may
market them as isolation. The threat model therefore concentrates on: leakage
to *broader* audiences (world-readable files, logs, process args, SQLite,
uploaded diagnostics), corruption of user state, and attacker-influenced data
crossing the parse boundary.

### 3.1 Key material at rest

| Location | Contains | Discipline |
| --- | --- | --- |
| Keychain items (per profile) | raw key | Created by the app; no secret ever in `argv` (§3.5); never exported, backed up, or synced by us |
| `config.yaml` | raw keys + mgmt secret | 0600-from-birth, atomic publish — existing precedent (#431); unchanged posture |
| Config backups (new) | raw keys + mgmt secret | ModelDeck state dir, 0600-from-birth, bounded count, pruned; named as secret-bearing in the build item's tests |
| `settings.json` / shell env file | helper **command string** only | No secret; pointer-only property preserved (fetch at shell start, xtrace suspended) |
| SQLite | **no key material** | Only labels, `client_key_map` SHA-256 hashes of our own 256-bit random keys (preimage-infeasible, not credentials); tripwire test extended |
| Daemon memory/logs | tick-local hash only | Raw key from the queue record is hashed on parse and dropped; counts-only logging contract stands ([usage-queue-consumer.mjs:155-160](../src/usage-queue-consumer.mjs)) |

### 3.2 Key material in flight

Keys travel only as loopback HTTP Authorization/x-api-key headers to
127.0.0.1. Existing guards carry over verbatim and are asserted in tests: the
key pointer is only wired when the base URL is a local CLIProxy
(`cliproxyRouted`, [service.mjs:4157-4160](../src/service.mjs)); a foreign base
URL refuses the wire outright ([service.mjs:4110-4126](../src/service.mjs)); the
shell block exports nothing when the item is missing and unsets a stale managed
key. Per-profile keys change the *item name*, never these predicates. The
consent screen and docs never instruct the user to paste a key anywhere.

### 3.3 Config write path

Threats: corrupting the user's config (A5), a torn/partial write, a
world-readable window, a write racing the proxy's own reload, our rollback
deleting user entries.
Mitigations, all named in §2.6: separate consent-gated operation (seed path
untouched); parse-locate-append-reverify with refuse-before-write on anything
unexpected; mkstemp+rename atomicity, 0600 enforced (tighten-or-refuse, §2.6); backup outside the proxy
dir so the write guard's two-destination allowlist is unchanged; removal
driven by the provisioning record with refuse-on-duplicate — never by value
match alone (§2.6); every outcome reported, never silent (0008).
The guard's tripwire tests extend to the new operation: its only proxy-dir
write destination is `config.yaml`, and an auth-dir path still throws the named
violation.

### 3.4 Ingest parsing of attacker-influenceable data

The riders deliberately import two fields that originate **outside** ModelDeck
(provider responses — or whatever upstream a user-configured proxy actually
talked to) plus a client-chosen `api_key`. All three are treated as hostile:

- **Structural bound first:** the allowlist parser remains the only door;
  everything not explicitly extracted stays discarded. Raw `response_headers`
  never persist.
- **Request-Id:** length cap + charset allowlist (§2.3). Because the deck is a
  loopback webview (0004), any stored string that renders in UI is an XSS
  vector — the charset allowlist kills script-bearing payloads at ingest, and
  UI rendering still escapes as normal (defense in depth, not either/or).
- **Rate-limit values:** numeric clamp / enum allowlist / bounded-window
  timestamp (§2.4); a hostile header can at worst produce NULL, never a stored
  blob, never a log line containing the value, never a crash (parsers throw per
  record, and a malformed record is counted and skipped as today).
- **`api_key` spoofing:** any local process holding profile A's key can wear it
  — attribution is honest-participant-grade (§3 baseline). Unknown keys
  resolve NULL and their values are never stored, so an attacker cannot use the
  key field to smuggle chosen plaintext into SQLite. SQL is parameterized
  throughout ([db.mjs:1430-1438](../src/db.mjs)).

### 3.5 Keychain access

- **Creation:** the app writes items without the secret in `argv` — either
  SecItemAdd in-process, or `/usr/bin/security -i` with the command fed over
  stdin. **Landmine (verification item V5):** ACLs differ by creator — an item
  created via SecItemAdd by the app may trigger a Keychain prompt when the
  shell's `/usr/bin/security` reads it, which would break headless children
  (the exact problem the helper exists to solve, #277). The build item must
  prove the create-path/read-path pair is prompt-free before shipping; the
  stdin-fed CLI path is the recommended default since today's working item is
  CLI-created. The proof runs against a **scratch keychain**
  (`security create-keychain`), never the live login Keychain
  (never-compromise #1's spirit and this lane's own ban), with the recorded
  caveat that login-keychain ACL behavior may differ from a scratch keychain's
  — the scratch result is necessary evidence, not sufficient (review nit 9).
- **Read:** unchanged pattern — absolute `/usr/bin/security` path (no PATH
  resolution for a credential read), xtrace suspended, value never touches disk.
- **Injection:** the only new interpolated value in any command/settings string
  is the profile **slug**, generated by us from a restricted charset (§2.1) —
  free-text labels never enter a command string. Asserted by test.

### 3.6 Cross-profile leakage and mis-attribution

- Keychain items are same-user-readable across profiles — restated: not an
  isolation boundary. What the design does guarantee: **wiring integrity** (the
  helper slug is generated from the same authority that created the key; wire
  verifies the helper against the profile's recorded written state and mutates
  record-matched helpers only — §2.5), and
  **honest failure** (missing item → no export → requests fall to the profile's
  stored OAuth or fail visibly; never a silent fall-through to another
  profile's key).
- Inherited env: a child shell keeps its parent session's key across a profile
  switch (the #278 nested-shell rule) — attribution follows the launching
  profile, which is the correct semantic, and the stale-key unset discipline
  already covers the item-vanished case.
- The label stored per row is the ingest-time label; a renamed profile's
  history keeps the old label rather than being rewritten (D4).

### 3.7 What is explicitly out of reach

Proxy auth files (0006 — untouched; `api-keys` lives in `config.yaml`, and the
write guard proves it). Provider OAuth (0016). Live ports 8317/3867 in any
suite (never-compromise #2 — all new compat checks run against spawned isolated
instances with placeholder keys). No quota is spent by any part of this design,
build, or its tests (0032, never-compromise #1).

## 6. Open decisions for Tim (recommendation + evidence each)

- **D1 — Where the key→label mapping lives.** *Recommend:* daemon-owned SQLite
  table of SHA-256 hashes (§2.2). *Evidence:* resolution must be transactional
  with ingest (`ingestRequestUsage` is one BEGIN IMMEDIATE transaction,
  [db.mjs:1440](../src/db.mjs)); a separate state file adds a second
  consistency domain and its own locking. The hashes are not credentials; the
  discard-hardening invariant (per-request `api_key` never stored) is
  unaffected. *Alternative if you want zero key-derived data in SQLite:* a 0600
  JSON state file in the daemon dir, at the cost of a read-at-tick and a
  crash-consistency story.
- **D2 — Write-guard scope for backups.** *Recommend:* keep the guard at
  exactly two proxy-dir destinations; backups live in ModelDeck's state dir
  (§2.6). *Evidence:* the guard's strength is its enumerability
  ([ManagedProxy.swift:88-92](../macos/ModelDeckMac/Sources/ModelDeckMacCore/ManagedProxy.swift));
  every widening is a permanent enlargement of the auditable surface, and the
  backup has no functional need to sit in the proxy dir.
- **D3 — Restart choreography.** *Recommend:* user-triggered "restart now" on
  the consent screen for managed proxies, honest pending state for coexist;
  never an automatic bounce (live streams die on restart — the standing
  rebalancer rule). *Evidence:* V3 may moot this entirely (hot-reload); until
  proven, the no-automatic-restart posture is the only one that can't kill a
  2-hour agent run.
- **D4 — Label semantics on rename** (clarification of the label ruling, not a
  relitigation): rows keep their ingest-time label; the `client_key_map`
  carries the stable profile id, so a "re-label history on rename" migration
  stays *possible* later without storing anything beyond the ruling today.
  *Recommend:* accept as-at-ingest history; revisit only if renames prove
  common.
- **D5 — Claude-first scope.** *Recommend:* ship Claude-only; file the Codex
  marker (item 9). *Evidence:* Codex routing is user-owned and unmanaged today
  (the recorded asymmetry) — there is no ModelDeck-written surface to attach a
  per-profile key to without first building managed Codex routing, which is its
  own adjudication.
- **D6 — Legacy shared item disposal.** *Recommend:* leave the user-created
  shared Keychain item in place, offer removal in the migration UI, never
  delete automatically. *Evidence:* ModelDeck did not create it (§1); deleting
  a user-created credential container unasked violates the same instinct as the
  never-modify-config rule.
